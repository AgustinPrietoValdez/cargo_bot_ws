Lecture 02 · Phase 0 · Middleware

How nodes find each other: DDS, the Discovery Server and QoS

Learning goal. In Lecture 01 nodes magically "published" and "subscribed". Now we go under the hood: how do two processes actually discover each other over the network, and once they do, what decides whether a message is delivered? You will understand DDS, why cargo_bot needs a Discovery Server, the DOMAIN_ID, and QoS — and you will be able to debug "I can't see the topic".

1. Discovery vs delivery: two separate jobs

Concept

The middleware does two distinct things we must not confuse:

  • Discovery — how participants find each other and learn who publishes what (sections 4–6).
  • Delivery (QoS) — once they know each other, with what guarantees data is sent (section 8).

"I can't see the topic" is almost always a discovery problem; "the topic exists but no messages arrive" is almost always a QoS problem.

2. There is no master

Concept

ROS1 had a central roscore where everyone registered. ROS2 has none. Instead it uses DDS (Data Distribution Service), an industrial peer-to-peer standard. More robust (no single process to kill) but it creates the problem of this lecture: with no directory, how does a node find the others?

3. DDS and the layer stack

ROS2 talks to DDS through an abstraction layer so it can use different DDS vendors:

Your code (rclpy / rclcpp)
  -> rcl (C core)
  -> rmw (ROS middleware interface)     "talk to ANY DDS"
  -> rmw_fastrtps_cpp                    <-- the plug cargo_bot uses
  -> Fast DDS (eProsima)                 the real DDS moving bytes
  -> UDP / shared memory / the network
In cargo_bot

We pin RMW_IMPLEMENTATION=rmw_fastrtps_cpp so every process uses Fast DDS. Mixing RMWs can still work (it is the DDS-RTPS standard underneath) but pinning avoids config surprises.

4. The default: Simple Discovery (multicast)

Concept

By default Fast DDS uses multicast: on startup each participant shouts "I exist, I publish X" to a multicast address; everyone listening builds the who-publishes-what map, then switches to unicast for details. Works great on a normal LAN. Its weakness: it needs multicast UDP to flow between processes.

5. Why the default breaks in this project

Trap

cargo_bot runs across a boundary: Isaac Sim on Windows, the ROS2 nodes in WSL2 (virtualized Linux). The Windows↔WSL2 link is a NAT/virtual interface where multicast UDP does not propagate reliably. With Simple Discovery the two sides never see each other — topics never appear, ros2 topic list is incomplete.

6. The fix: Discovery Server (unicast, client–server)

Concept

Fast DDS offers a Discovery Server: one process is the server at a fixed IP:port; everyone else is a client that connects by unicast to register and learn the others. It is a directory again — but only for discovery. The actual data still flows peer-to-peer; the server is not a data bottleneck.

In cargo_bot
  • WSL = SERVER on 127.0.0.1:11811 (start_discovery_server.sh).
  • Isaac = CLIENT (address patched by launch_isaac_ros.cmd).
  • WSL nodes = clients (via source_ros_wsl.sh).

Boot order matters: server first, then Isaac, then nodes. Start a client with no live server and it discovers nothing.

7. DOMAIN_ID: isolated rooms

Concept

The ROS_DOMAIN_ID (an integer) is a logical partition: participants in different domains do not see each other, even on the same network (it maps to different UDP ports — real isolation). It keeps two projects/robots from stepping on each other.

Trap

cargo_bot uses ROS_DOMAIN_ID=1 (NOT 4, which was another project). Both WSL and Isaac must share it, or they never discover each other even with the server correct. First suspect when "everything looks fine but I see nothing".

8. QoS: does the message actually arrive?

Concept

QoS (Quality of Service) sets delivery guarantees. The rule that bites everyone: if publisher QoS and subscriber QoS are incompatible, they do not connect, even though the topic exists. Three policies you will touch:

  • Reliability: RELIABLE (retransmit, for commands/maps/TF) vs BEST_EFFORT (drop-ok, for high-rate sensors like /scan, /odom, /particle_cloud).
  • Durability: VOLATILE (only future samples) vs TRANSIENT_LOCAL (keep last sample for late joiners — this is "latched", used by /map).
  • History: KEEP_LAST(depth=N) vs KEEP_ALL.

The reliability compatibility matrix — memorize it:

PublisherSubscriberConnects?
RELIABLERELIABLEyes
RELIABLEBEST_EFFORTyes
BEST_EFFORTBEST_EFFORTyes
BEST_EFFORTRELIABLENO
Trap — the one that bit you

In Phase 4, RViz showed incompatible QoS … RELIABILITY on /particle_cloud and the AMCL cloud did not appear. Cause: AMCL publishes BEST_EFFORT, RViz requested RELIABLE → bottom row of the matrix. Fix: set the RViz display to Best Effort.

9. How this maps to the boot sequence

In cargo_bot

source_ros_wsl.sh exports ROS_DOMAIN_ID=1, RMW_IMPLEMENTATION=rmw_fastrtps_cpp and the discovery-server variables (source it in every WSL terminal). Boot: (1) discovery server, (2) Isaac + Play, (3) ROS2 nodes. Break the order → "topics do not appear".
