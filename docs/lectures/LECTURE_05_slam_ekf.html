SLAM, the EKF and the TF tree

1. The problem SLAM solves

Concept

SLAM = Simultaneous Localization And Mapping. A chicken-and-egg problem: to build a map you need to know where you are; to know where you are you need a map. SLAM does both at once — as the robot moves, it incrementally builds a map and estimates its pose in it, from the lidar (/scan_fixed) plus a motion estimate (odometry).

cargo_bot runs SLAM once to produce the saved map (cuarto_v1), then switches to pure localization (AMCL, Lecture 06). SLAM and AMCL are never run together (both own map → odom).

2. slam_toolbox: scan-matching into an occupancy grid

Concept
  • Scan matching: align each new lidar scan against the accumulated map to estimate motion more precisely than odometry alone.
  • Occupancy grid: a 2D array where each cell is free / occupied / unknown — the /map, saved as cuarto_v1.pgm (image) + .yaml (resolution, origin, thresholds).
  • Loop closure: when the robot revisits a place it recognizes it and corrects accumulated drift, snapping the map consistent.

slam_toolbox publishes the map → odom transform — the correction between drifting odometry and the true map.

3. Why an EKF: fusing odometry + IMU

Concept

Wheel odometry drifts (slip, imperfect radii), especially in heading. An IMU gives angular velocity/orientation directly but drifts in position. Neither alone is enough. The Extended Kalman Filter (robot_localization's ekf_node) fuses them, weighting each by its uncertainty, and outputs the odom → base_footprint transform (smooth, locally accurate) plus /odometry/filtered.

So localization is layered: EKF gives smooth local pose; SLAM/AMCL correct global drift on top.

4. The TF tree: one publisher per edge

This is the rule that ties everything together and the #1 source of "the robot jumps in the map" bugs.

Concept
  • map → odom: SLAM (mapping) or AMCL (localizing) — never both.
  • odom → base_footprint: the EKF. Never touched by SLAM/AMCL.
  • base_link → sensors/wheels: Isaac / robot_state_publisher (URDF).

Two publishers on one edge → contradictory transforms → visible "teleporting"/ oscillation. This is exactly why slam_toolbox and AMCL never run together.

5. cargo_bot-specific gotchas

Traps that cost real time
  • EKF yaw anchor. ekf.yaml fuses the IMU's absolute yaw as a heading anchor; without it the live scan drifted ~15° from the map. Valid in sim and with a BNO085-class IMU; with a raw MPU6050 you would disable it and anchor heading via SLAM/AMCL.
  • The lidar "disaster". A suggested +90°-X rotation broke the lidar; the real cause of the garbage map was a scene with no walls. Fix: add walls + keep identity orientation.
  • 1066 vs 1067 scan count → scan_angle_fixer (Lecture 04).
  • Stop/Play resets /clock → the EKF loses time continuity and dies; Ctrl+C and relaunch.

6. The end state of Phase 3

In cargo_bot

Isaac publishes /scan /odom /imu/data /clock; scan_angle_fixer gives /scan_fixed; the EKF publishes odom → base_footprint + /odometry/filtered; slam_toolbox built and we saved cuarto_v1.{pgm,yaml}. That saved map is the input to Phase 4 localization (AMCL).
