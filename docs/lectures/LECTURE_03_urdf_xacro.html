Describing the robot: URDF and xacro

Learning goal. Understand how a robot is described to ROS as a tree of links and joints, why we author it in xacro (not raw URDF), what inertias are for, and the base_footprint/base_link convention. Then read cargo_bot's model and know why the wheels once "froze".

1. Why a robot model at all?

Concept

Before simulating, localizing or navigating, every piece of software must agree on the robot's geometry and kinematics: where the lidar sits relative to the wheels, the wheel separation, where the robot's "center" is on the floor. URDF (Unified Robot Description Format) is the XML that encodes this. From it, ROS publishes the TF tree — the live transforms between frames that SLAM, Nav2 and RViz all rely on.

If the URDF is wrong (wheel separation off, lidar misplaced), everything downstream is subtly wrong: odometry drifts, the scan does not line up with the map. Foundational, not cosmetic.

2. The two building blocks: links and joints

Concept
  • <link> = a rigid body. Up to three parts: visual (the mesh you see), collision (shape for physics, often simpler), inertial (mass + inertia + center of mass).
  • <joint> = how two links connect (a parent and a child). Its type sets the allowed motion: fixed (rigid), continuous (unlimited rotation — drive wheels), revolute (limited rotation — a hatch), prismatic (slide).

The model is a tree: exactly one root, no cycles.

4. base_footprint vs base_link (a convention that matters)

Concept

base_link = the physical body frame (origin at the chassis). base_footprint = a frame on the ground directly under the robot, no roll/pitch — the robot's "shadow". Navigation reasons in 2D on the floor, so it wants a clean ground-level reference that does not bob with the chassis.

In cargo_bot

The whole Nav2/AMCL stack is configured with robot_base_frame: base_footprint (NOT base_link) — the detail flagged all over the Phase 4 config. The fixed base_footprint → base_link joint encodes the chassis height. Follows REP-105.

5. Inertias: the part beginners skip and regret

Concept

The <inertial> block (mass, center of mass, 3×3 inertia tensor) is ignored by RViz but critical for physics (Isaac). Zero or nonsensical inertia → the robot jitters, flips or explodes in sim.

Deeper

Computing inertia tensors by hand for every shape is tedious, so the project uses xacro macros (inertial_macros.xacro: xacro:inertial_box, inertial_cylinder…) that compute the tensor from mass + dimensions. You call the macro; it fills in the math.

6. Why xacro instead of raw URDF

Concept

Raw URDF is verbose and repetitive. xacro (XML Macros) adds <xacro:property> (variables like wheel_radius), <xacro:macro> (reusable blocks, e.g. one wheel macro called left/right), and <xacro:include> (split across files).

In cargo_bot

Split for clarity: cargo_bot.urdf.xacro (top, the source of truth) includes chassis.xacro, wheels.xacro, sensors.xacro, inertial_macros.xacro. xacro is not a runtime format — it must be expanded:

xacro src/cargo_bot_description/urdf/cargo_bot.urdf.xacro > /tmp/cargo_bot.urdf
check_urdf /tmp/cargo_bot.urdf      # sanity-check the tree

In launch files, robot_state_publisher expands it live (the Command(['xacro ', ...]) substitution) and publishes /robot_description plus the fixed-joint TF.

7. The Isaac import path (and the frozen-wheels gotcha)

Isaac cannot import xacro directly. The Phase 2 workflow: expand to a flat URDF, fix mesh paths for Windows, import that (the generated cargo_bot_isaac.urdf at the repo root — a generated artifact, not a source).

Trap — frozen wheels

After import the robot accepted /cmd_vel but the wheels did not turn. Cause: the wheel joint's PhysX velocity drive had damping=0, stiffness=0 → no torque applied. Fix (scripts/maintenance/fix_wheel_drives.py): damping=1000, stiffness=0, type=force. Moral: a model that is kinematically correct can be dynamically dead if the drive params are wrong.
