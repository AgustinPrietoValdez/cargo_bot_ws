1. What ROS2 is (and is not)

Concept

ROS2 is not an operating system, despite the name (Robot Operating System). It runs on top of your OS (Linux/Windows). It is a framework + middleware + toolset for writing robot software:

  • Middleware — a standard way for many programs to talk over the network (the "plumbing"; deep dive in Lecture 02).
  • Client libraries — rclpy (Python) / rclcpp (C++) so you write nodes without reinventing communication.
  • Conventions + packages — agreed message formats, coordinate-frame rules (REP-105), and thousands of ready-made packages (SLAM, navigation, drivers).
  • Tools — CLI (ros2 ...), visualization (RViz), recording (rosbag), build system (colcon).

Analogy: ROS2 is to robotics what a web framework is to websites — it doesn't replace your computer, it gives you the structure and parts so you build the robot, not the plumbing.

Why does it exist? Every robot needs the same hard things: read sensors, pass data between processes, transform coordinate frames, log, run controllers. Without a framework you rewrite all of that per robot. ROS2 standardizes it so the community shares parts. We are on ROS2 Humble (an LTS release).

2. The big idea: a robot is many small programs (the compute graph)

Concept

A ROS2 robot program is not one big program. It is many small programs running at the same time, each doing one job, talking to each other. Each small program is a node. The set of running nodes plus the connections between them is the compute graph.

Why split it? Modularity and robustness. One node reads the lidar, another builds the map, another plans paths. You can restart, replace or debug one without touching the others. If the planner crashes, the lidar driver keeps running. You can even move a node to another machine and nothing else changes.

3. What a node is

Concept

A node is a single unit of computation — in practice usually one running process — responsible for one focused job ("publish laser scans", "estimate the pose"). A node has a name, lives in the graph, communicates with others over named channels (it does not call their functions directly), and is kept alive by an executor that "spins" it — loops forever processing incoming messages and timers.

Analogy: a node is one employee with one job. They don't walk into each other's offices; they leave mail in labeled mailboxes (topics) or file formal requests (services). "Spinning" is the employee sitting at their desk, checking the inbox and acting.

import rclpy
from rclpy.node import Node

class MyNode(Node):
    def __init__(self):
        super().__init__('my_node')          # <-- the node's NAME
        self.get_logger().info('hello')

rclpy.init()
rclpy.spin(MyNode())                          # <-- the executor keeps it alive (the "spin")
Deeper — the executor & callbacks

A node is event-driven: you register callbacks (a function to run when a message arrives, or a timer fires). The executor is the loop that watches all of them and calls the right callback. Two kinds matter later:

  • SingleThreadedExecutor (default) — one callback at a time, in order. Simple, but a slow callback blocks the rest.
  • MultiThreadedExecutor + callback groups — lets callbacks run concurrently. A reentrant callback group allows a node to, say, handle a service request while a timer keeps publishing. Several nodes in cargo_bot's ecosystem use this pattern so a long operation doesn't freeze their heartbeat.

Takeaway: "the node is running" really means "its executor is spinning, dispatching callbacks". If a node seems dead, its spin is blocked or it never reached spin().

4. A node's attributes, one by one

This is the heart of "what is a node". A node is defined by these attributes:

AttributeWhat it isEveryday analogy
NameUnique identifier in the graph, e.g. /amcl. The name on the office door.
NamespaceOptional prefix grouping/isolating a node and its topics, e.g. /robot1/amcl. Run two robots without clashes.The department the office is in.
PublishersOutgoing channels it writes to (topic + message type). "I produce this data."Outboxes it drops mail into.
SubscriptionsIncoming channels it reads, each with a callback run per message. "I consume this data."Inboxes it watches.
Service servers / clientsRequest–response endpoints (§6): offer a service, or call someone else's.A help desk you staff, or one you phone.
Action servers / clientsLong-running goals with feedback (§7). Assigning a multi-step project with progress reports.
ParametersNamed config values read at startup/runtime, e.g. use_sim_time (§8).The settings on the desk.
TimersCallbacks on a fixed rate ("publish at 20 Hz"). An alarm: "do this every X seconds".
Logger / clockEvery node can log and read time (real or simulated — what use_sim_time switches).A notebook and a wall clock.

Crucially, nodes never call each other's functions. Node A does not "call" node B; A publishes to a topic and B happens to subscribe. They are decoupled — neither knows who is on the other side. That decoupling is what makes the graph swappable and robust.

Deeper — lifecycle (managed) nodes

Some nodes are managed lifecycle nodes: they have explicit states (unconfigured → inactive → active) and only run when something "activates" them. This lets a system bring components up in a controlled order. All of Nav2's servers are lifecycle nodes brought up by a lifecycle_manager — that's why in Phase 4 you checked ros2 lifecycle get /amcl expecting active. We return to this in Lecture 06.

5. Topics & messages (the most common way nodes talk)

Concept

A topic is a named bus for a continuous stream of data, e.g. /scan. A node publishes messages to it; any node that subscribes receives them. It is asynchronous (fire and forget), many-to-many (multiple pubs/subs share a topic), and typed (one message type per topic).

Analogy: a radio station. It broadcasts on a frequency (the topic); anyone tuned in hears it; the broadcaster doesn't know who's listening.

Deeper — interfaces (.msg / .srv / .action)

The "type" of a topic is a message defined in a .msg file: a typed struct, e.g. sensor_msgs/msg/LaserScan has fields angle_min, ranges[], etc. Services use .srv (request + response) and actions use .action (goal + result + feedback). Collectively these are interfaces. Inspect any of them with ros2 interface show sensor_msgs/msg/LaserScan. A publisher and subscriber must agree on the exact type or they won't connect.

In cargo_bot

Isaac publishes /scan (LaserScan), /odom (Odometry), /imu/data, /clock. scan_angle_fixer subscribes /scan and publishes /scan_fixed. Topics are ~90% of how our nodes talk. (Full graph in §10.)

6. Services (request → response)

Concept

A service is a one-off request that expects a reply, synchronously: a client sends a request, the server acts and replies, done. For short queries/commands ("clear the costmap", "is this path valid?"), not for streams.

Analogy: a phone call with a yes/no answer, versus a topic's radio broadcast.

7. Actions (long-running goals with feedback)

Concept

An action is for a goal that takes time where you want feedback and the ability to cancel: send a goal, get periodic feedback, get a final result. Built on top of topics + services.

Analogy: food delivery — place the order (goal), get "on the way" updates (feedback), can cancel, finally "delivered" (result).

In cargo_bot

"Navigate to this goal pose" is an action (NavigateToPose): seconds long, streams distance-remaining feedback, cancellable. Clicking the goal in RViz made you a client of that action server inside bt_navigator.

8. Parameters (a node's configuration knobs)

Concept

Parameters are named values a node reads to configure itself, usually from a YAML file at launch. They change behavior without editing code.

In cargo_bot

Every node takes use_sim_time: true — use Isaac's simulated /clock, not the wall clock. The whole nav2_params.yaml is parameters: AMCL's scan_topic, the costmap's inflation_radius, DWB's max_vel_x. Tuning (Lecture 06) is mostly editing parameters.

9. Seeing the graph with the CLI

You can inspect the live graph — these are your everyday debugging commands:

ros2 node list                 # every running node
ros2 node info /amcl           # one node's pubs, subs, services, params
ros2 topic list                # every topic
ros2 topic info /scan_fixed -v # a topic's type + who pubs/subs (and their QoS)
ros2 topic echo /scan_fixed    # print messages as they arrive
ros2 topic hz /clock           # measure publish rate
ros2 interface show sensor_msgs/msg/LaserScan   # see a message's fields
Trap

If ros2 node list / topic list is empty or incomplete, the nodes are running but not discovering each other — a middleware problem (wrong ROS_DOMAIN_ID, discovery server down, or a QoS mismatch). That's exactly Lecture 02.

10. The cargo_bot graph: who talks to whom

Here is the real navigation graph of our robot. Solid teal arrows are topics (data streams); dashed purple arrows are TF (coordinate transforms — Lecture 04). Read it left to right: Isaac produces sensor data, it flows through localization and planning, and a velocity command flows back to Isaac to drive the wheels.

In cargo_bot — reading the graph
  • Isaac publishes raw sensors (/scan, /odom) and subscribes /cmd_vel to move.
  • scan_angle_fixer repairs the scan → /scan_fixed (consumed by amcl and the Nav2 costmaps).
  • ekf_filter_node fuses /odom + IMU and publishes the TF odom→base_footprint.
  • map_server serves the saved map on /map; amcl localizes and publishes the TF map→odom.
  • Nav2 servers plan + follow the path, output cmd_vel_nav → twist_mux → /cmd_vel → back to Isaac. The loop is closed.

"Launching the robot" = starting this graph (via launch files), each node reading its parameters and wiring these exact topics/TF.
