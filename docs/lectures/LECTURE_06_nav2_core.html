Lecture 06 · Phase 4a · Navigation

Nav2 core: how the robot navigates

Learning goal. Understand Nav2 as cooperating lifecycle servers orchestrated by a behavior tree: AMCL (localization), costmaps (world model), NavFn (global planner), DWB (local controller), and twist_mux (command arbitration). By the end you can explain what each node does when you click a goal.

1. The big picture: from a goal click to wheel motion

Concept

Nav2 is not one program — it is several lifecycle nodes (servers), each doing one job, brought up in order by lifecycle managers. Understanding the division of labor is the key.

2. AMCL: localizing against the saved map

Concept

AMCL (Adaptive Monte Carlo Localization) is a particle filter: scatter many pose hypotheses ("particles"), weight each by how well the lidar matches the map, resample toward the good ones, converge. The cloud tightening on the robot = high confidence (the "little arrows" in RViz).

In cargo_bot

AMCL publishes map → odom (same edge SLAM used — why they cannot co-run). It needs an initial pose (cannot solve the global "kidnapped robot" from scratch): set_initial_pose: true with (0,0,0) (the confirmed spawn). Uses /scan_fixed, base_footprint, DifferentialMotionModel.

3. Costmaps: the robot's model of the world

Concept

A costmap is a grid where each cell holds a cost (how bad to be there). Nav2 runs two: global_costmap (whole map, frame: map, for the planner) and local_costmap (small rolling window, frame: odom, for real-time avoidance). Built from layers: static (the saved map), obstacle (live from /scan_fixed), inflation (a cost halo around obstacles for clearance).

4. Planner (NavFn) vs Controller (DWB): global vs local

Concept
  • planner_server / NavFn = the global planner. Given start + goal + global costmap, compute the full route (Dijkstra/A*). It plans, it does not drive.
  • controller_server / DWB = the local controller. 20×/s it samples short candidate trajectories, scores each with critics (stay on path, reach goal, avoid obstacles, do not oscillate), and emits the best velocity. DWB is what dodges a chair that appears.

DWB outputs to cmd_vel_nav (remapped), not directly to /cmd_vel — so it goes through the mux.

5. Behaviors, the BT, and lifecycle managers

Concept
  • behavior_server — recovery behaviors (spin, backup, wait) when stuck. It also publishes velocity (the harmless second /cmd_vel publisher you saw).
  • bt_navigator — runs a behavior tree (XML) orchestrating "compute path → follow → if stuck, recover → retry".
  • lifecycle managers — Nav2 nodes are managed (unconfigured → inactive → active); a manager brings a group up in order, autostart: true activates them. cargo_bot has two: localization (map_server, amcl) and navigation (controller, planner, behavior, bt, waypoint). Stuck in inactive = manager order or a bad plugin.

6. twist_mux: arbitrating who drives

Concept

Multiple sources may command the robot (Nav2 now; joystick + e-stop later). twist_mux forwards the highest-priority active input to /cmd_vel.

In cargo_bot

One input today: navigation (cmd_vel_nav, priority 10). Set up early so adding joystick (100) / e-stop (255) in Phase 4b needs no refactor. The controller's remap (cmd_vel → cmd_vel_nav) feeds the mux; the mux's cmd_vel_out → /cmd_vel feeds Isaac.
