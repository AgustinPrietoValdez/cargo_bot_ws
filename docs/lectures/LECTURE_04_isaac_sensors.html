Isaac Sim, OmniGraph and the ROS2 bridge

Learning goal. Understand what Isaac Sim is (USD + PhysX), how an OmniGraph wires a simulated sensor to a ROS2 topic, and the specifics of the lidar, IMU and the /cmd_vel chain — including the gotchas that cost real debugging time. By the end you can explain how a /scan message is born inside Isaac.

1. What Isaac Sim is

Concept

NVIDIA Isaac Sim is a robotics simulator on the Omniverse platform. Two pillars:

  • USD (Universal Scene Description) — the scene format. Everything (robot, room, sensors, lights) is a tree of prims under a root. Our scenes are scene_v<N>.usda (current: scene_v4.usda).
  • PhysX — the physics engine (rigid bodies, joints, drives, collisions).

Two sensor pipelines live inside, and confusing them is a classic mistake: PhysX sensors (IMU, contact — from physics state) and RTX sensors (lidar, camera — ray-traced on the GPU; these need a Render Product).

2. The /World convention (silent-failure trap)

Trap

The robot prim must live under /World/<robot>/…. Place it without the /World wrapper and the RTX sensor pipeline fails silently — no error, but no /scan. Always /World/cargo_bot/….

3. OmniGraph: the visual wiring between Isaac and ROS2

Concept

Isaac does not magically publish ROS2 topics. You build an OmniGraph (Action Graph): a node graph where data flows from a tick, through sensor-reader nodes, into ROS2-publisher nodes. Bridge nodes live under isaacsim.ros2.bridge.* (Isaac 5.1; older omni.isaac.ros2.* docs do not apply).

Every publishing graph needs: a tick (OnPlaybackTick, fires per sim frame), a ROS2Context (provides DDS context/DOMAIN_ID), and a simulation-time source feeding the message timestamp (so use_sim_time works downstream).

Trap

No tick → no messages. Nothing publishes unless Isaac is in Play. (This is why "map does not appear" so often traces back to "Isaac is not in Play".)

4. The RTX lidar → /scan

Trap — the off-by-one

Isaac's RTX lidar emitted 1066 readings while slam_toolbox expected 1067, so SLAM rejected every scan. Fix: a republisher node scan_angle_fixer that rewrites the metadata and outputs /scan_fixed. That is why the whole downstream stack subscribes to /scan_fixed, never /scan.

5. The IMU → /imu/data

Concept

The IMU is a PhysX sensor (no Render Product). Chain: OnPlaybackTick → IsaacReadIMU → ROS2PublishImu, with ROS2Context and a simulation-time feed for the timestamp.

Trap

IsaacReadIMU.inputs:imuPrim is a target attribute, not a string. Bind it with og.Controller.set(attr, [usdrt.Sdf.Path(...)]) — a list of paths — or it fails silently. Captured in scripts/setup/add_imu.py; verify with ros2 topic hz /imu/data (~100 Hz).

6. The /cmd_vel → wheels chain (closing the loop)

Concept

To drive, the bridge subscribes /cmd_vel and converts it to wheel commands:

SubscribeTwist(/cmd_vel) -> Break3Vector x2
   -> DifferentialController(wheelDist=0.29, wheelRadius=0.1)
   -> ArticulationController(joints=[left_wheel_joint, right_wheel_joint])

The DifferentialController does the diff-drive math (linear.x + angular.z → each wheel speed); the ArticulationController applies it. Recall Lecture 03: this only moves if the wheel drives have proper damping/stiffness.

7. The boot picture

In cargo_bot

Isaac runs these graphs → publishes /clock /scan /odom /imu/data /tf, subscribes /cmd_vel. scan_angle_fixer bridges /scan → /scan_fixed. Everything is timestamped with sim time; downstream nodes run use_sim_time:=true.

Trap

Pressing Stop/Play resets /clock, which kills the EKF's time continuity → Ctrl+C and relaunch the ROS2 side. (Why the EKF is clock-sensitive: Lecture 05.)
